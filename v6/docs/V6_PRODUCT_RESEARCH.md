## 二、关键发现：空白地带

### 2.1 没有人做"图表内语义标注+自动统计"闭环

所有产品都有画线工具，但**绘制 ≠ 标注**：

- 画一个矩形 → 系统只看到像素坐标 `(x1, y1, x2, y2)`
- 系统不知道这个矩形是 FVG
- 系统不知道 FVG 的上下边界和 CE
- 系统不知道这个 FVG 跟哪个入场关联
- 因此无法按 FVG 维度统计胜率

**现有产品的绘制层是装饰品，不是数据。**

### 2.2 通用产品不可能做 SMC/ICT 垂直概念

TradeZella 有标签系统，但标签只有名字（"Setup A"），没有语义。他们不可能为 SMC/ICT 硬编码 FVG、OB、SSL、Liquidity Sweep 这些概念——因为他们的用户还有 swing trader、options trader、crypto trader。

**垂直 = 通用产品做不了 = 你的护城河。**

### 2.3 用户的真实痛点（来自自己的使用经验）

在 FXReplay 中练盘验证操作系统时：

1. 看到 FVG → 想记录"我在这里看到了 FVG"
2. **截图**（FXReplay 没有标注功能）
3. **打开 Excel/Notion**
4. **手动记录**：日期、品种、入场价、止损、目标、标签...
5. 继续回放
6. 到达出场点 → **再截图** → **再手动记录**
7. 练完后 → **自己算胜率、盈亏比**
8. 想要 AI 分析 → **把 Excel 数据喂给 ChatGPT**

**每个环节都是断的。标注脱离图表上下文，统计要手动做，AI 分析要自己搬数据。**

## 三、数据成本分析

### 3.1 当前数据资产

| 项 | 值 |
|----|-----|
| 数据库 | DuckDB (~945MB) |
| 表 | `futures_1m` |
| 品种 | ES, NQ |
| 粒度 | 1分钟（所有时间戳在整分钟边界） |
| 数据范围 | 2008-01-02 ~ 2026-06-23 |
| 总行数 | ~1,905万根 |
| NQ 典型交易日 | ~1,380 根 |
| 数据来源 | Databento + yfinance |
| 成本 | ¥400 一次性 |

### 3.2 不同粒度的成本对比

| 粒度 | ES 单日行数(23h) | 1年行数 | 10年行数 | DuckDB查询 | 大约数据成本 |
|------|-----------------|--------|---------|------------|-------------|
| **1分钟** | ~1,380 | ~504K | ~5M | ✅ 毫秒级 | ¥400（已购） |
| 10秒 | ~8,280 | ~3M | ~30M | ✅ 可行 | ~¥1,200-2,000/年 |
| 1秒 | ~82,800 | ~30M | ~300M | ⚠️ 需优化 | ~¥3,000-5,000/年 |
| tick | ~数百万 | ~数十亿 | ~数百亿 | ❌ 需专业方案 | ~¥10,000+/年 |

### 3.3 数据成本对比（5年总成本）

| 方案 | 数据成本 | 订阅成本 | 总成本 |
|------|---------|---------|--------|
| FXReplay Pro | $0（内置） | $35/月 × 60 = $2,100 | **¥15,120** |
| TradeZella Pro | $0（内置） | $49/月 × 60 = $2,940 | **¥21,180** |
| V6 + 1m数据 | ¥400 一次性 | ¥0 | **¥400** |
| V6 + 秒级数据 | ¥3,000-5,000/年 | ¥0 | **¥15,000-25,000** |

### 3.4 建议

**坚持 1m 数据，不做秒级数据管道。**

理由：
- SMC/ICT 方法的核心判断单位是 1 分钟 K 线结构
- 1m 数据 ¥400 覆盖 ES+NQ 从 2008 到 2026，已经是巨大资产
- 秒级数据成本是 1m 的数倍，需要重构整个 bar-data 管道
- 现有架构（bar-window, bar-window-cache, database-bars-adapter）全部为 1m 设计
- 如果将来确实需要秒级放大镜，可以按需加载单根 1m K 线对应的 60 秒数据（60 行，微秒查询），不需要全量秒级管道

## 四、产品定位建议

### 4.1 定位演进

```
之前：开源 SMC/ICT 回放练盘工作站
现在：开源 SMC/ICT 操作系统验证工作站

核心闭环：
  回放历史数据 → 在图表上标注你的判断 → 自动统计验证你的 edge
```

### 4.2 一句话差异化

> **FXReplay 让你在图表上画矩形，但不知道矩形是 FVG。**
> **TradeZella 让你给交易打标签，但标签和图表是断的。**
> **V6 让矩形就是 FVG，标签就在图表上，标注完自动统计你的系统有没有 edge。**

### 4.3 产品闭环

```
开盘前：用 V6 做 1m 练盘 → 标注你的系统规则 → 验证你的 edge
开盘时：用 Tradovate/你的 broker 实盘交易
收盘后：用 TradeZella 自动同步分析（统计、AI 标注）

三个工具各做各的最好：
  V6 = 本地练盘验证引擎（你的核心资产）
  Tradovate = 执行
  TradeZella = 实盘统计复盘
```

### 4.4 与竞品的关系

**互补，不是竞争。**

| 维度 | FXReplay | TradeZella | V6 |
|------|----------|-----------|-----|
| 核心问题 | 回放练盘 | 实盘统计 | **系统验证** |
| 数据来源 | 平台内置 | 经纪商导入 | **本地 DuckDB** |
| 数据主权 | 在他们服务器 | 在他们服务器 | **在自己机器** |
| 离线使用 | 否 | 否 | **是** |
| 开源 | 否 | 否 | **计划开源** |
| SMC/ICT 专注 | 部分 | 通用 | **专门设计** |
| 图表内标注 | ❌ | ❌ | **✅** |
| 语义标签 | ❌ | ❌（只有名字） | **✅（FVG/OB/SSL/Liquidity）** |
| 自动统计 | ✅ 基础 | ✅ 50+报告 | **✅ 按系统维度** |
| 成本 | $0~35/月 | $29~49/月 | **¥400 数据一次性** |

## 五、功能分层建议

### 5.1 第一层：标注 + 预设标签（MVP，预计 2-3 周）

```
不做任何自动识别。
用户在图表上标注入场，选择标签。

功能清单：
  1. 在图表上点击标注入场点（LC 画一个标记）
  2. 选择方向（多/空）
  3. 填写止损/目标（自动从点击价位填，可拖动调整）
  4. 选择系统标签（下拉：London Open FVG / NY AM / Asia 等，用户可自定义）
  5. 选择概念标签（多选：FVG / Displacement / OB / Liquidity Sweep 等）
  6. 选择止损类型（下拉：SSL / OB / 结构低）
  7. 选择目标类型（下拉：Liquidity / OB / 前高前低）
  8. 继续推演到出场，标出场点
  9. 自动计算 R 倍数
  10. 所有标注绑定到 K 线时间戳

数据模型：
  annotation = {
    id, type: "entry"|"exit",
    direction: "long"|"short",
    instrument, timestamp, timeframe,
    price, stopLoss: { type, price },
    takeProfit: { type, price },
    concepts: ["fvg", "displacement"],
    system: "london_open_fvg",
    session: "london",
    R: 2.9,
    exit: { timestamp, price, reason }
  }

技术实现：
  - Lightweight Charts 渲染入场/出场标记
  - LC 的 drawing API 画止损线/目标线
  - HTML 表单做标签选择
  - 标注数据存本地 DuckDB 或 JSON
  - LC 不需要理解 FVG，只需要画线
  - 你的代码理解语义，负责记录和统计
```

**这一层不需要 ICT 概念引擎。用户知道 FVG 是什么，代码只需要记录用户说的。**

### 5.2 第二层：标注关联 + 统计面板（1-2 周）

```
功能清单：
  1. 入场标注和止损线/目标线自动关联，拖动更新
  2. 点击统计面板中的任何一条记录 → 图表跳回那个位置
  3. 完整 5m/15m 视图上下文保留
  4. 单次 session 统计（胜率、盈亏比、期望值、R 分布）
  5. 多次 session 聚合统计

统计面板示例：
  ┌────────────────────────────┐
  │ 系统：London Open FVG       │
  │ 总标注数: 47次              │
  │ 胜率: 57.4% (27W/20L)      │
  │ 平均盈利: +4.2R             │
  │ 平均亏损: -1.1R             │
  │ 期望值: +1.62R/trade        │
  │                             │
  │ 按概念标签:                  │
  │  FVG + Displacement: 57.4%  │
  │  FVG + OB Mitigation: 48%   │
  │                             │
  │ 按止损类型:                  │
  │  SSL下方: 62% (18W/11L)     │
  │  OB下方: 53% (9W/8L)        │
  │                             │
  │ 按时段:                     │
  │  London Open: 57.4%         │
  │  NY AM: 52%                 │
  │                             │
  │ 按品种:                     │
  │  NQ: 61.9%                  │
  │  ES: 48%                    │
  └────────────────────────────┘
```

### 5.3 第三层：ICT 概念结构化（可选，以后做）

```
FVG 标注增强：
  用户画矩形 → 选择"FVG" → 弹出表单：
    上边界: (自动从矩形顶部填)
    下边界: (自动从矩形底部填)
    CE: (自动计算 = (上+下)/2)
    是否被 fill: [否 ▼]

OB 标注增强：
  用户画矩形 → 选择"OB" → 弹出表单：
    类型: [Bullish OB ▼]
    是否有 displacement 确认: [是/否]

自动识别（远期）：
  代码辅助识别 FVG/OB → 用户确认/修正 → 统计
```

**这是锦上添花，不是 MVP。第一版靠用户手动标注就够了。**

## 六、架构适配建议

### 6.1 标注中间层（在 LC 和数据之间）

```
┌──────────────────────────────────┐
│  Lightweight Charts（渲染层）     │  只管画
│  K线、缩放、平移、基础绘制         │
└──────────────────────────────────┘
         ▲
         │ 视觉指令（drawing API 调用）
┌──────────────────────────────────┐
│  标注中间层（新模块）              │  管语义
│  - 用户点击 → 创建标注记录          │
│  - 标注记录 → 调用 LC 画标记       │
│  - LC 拖动事件 → 更新标注记录       │
│  - 标注记录 → 存入本地存储          │
└──────────────────────────────────┘
         ▲
         │
┌──────────────────────────────────┐
│  统计层（新模块）                  │  管数据
│  - 从标注数据自动聚合              │
│  - 按系统/概念/时段/品种统计       │
│  - 不需要知道 LC 的存在            │
└──────────────────────────────────┘
```

**Lightweight Charts 负责画，你的代码负责意思。两层解耦。**

### 6.2 现有架构不需要大改

```
不需要改的：
  ✅ bar-data-runtime.js（1m 数据管道不变）
  ✅ bar-window.js（加载窗口管理不变）
  ✅ database-bars-adapter.js（V4 API 查询不变）
  ✅ replay-runtime（回放引擎不变）
  ✅ display-timeframe（5m/15m 投影不变）
  ✅ chart-viewport-runtime（视口管理不变）
  ✅ V4 API / DuckDB（数据层不变）

需要新增的：
  🆕 practice-markup-runtime（标注中间层）
  🆕 practice-stats（统计聚合）
  🆕 practice-session（练盘会话管理）
  🆕 LC 上的标注交互（drawing API + 事件监听）
```

### 6.3 数据存储建议

```
标注数据建议用本地 JSON 文件（或 SQLite），不混入 DuckDB：

  ~/.v6/practice/
    sessions/
      2026-07-10_london-open-nq.json    ← 一次练盘会话
      2026-07-11_ny-am-es.json
    annotations/
      2026-07-10_london-open-nq.json    ← 标注记录
    stats/
      aggregated.json                    ← 聚合统计缓存

理由：
  - 标注数据是用户行为数据，不是市场数据，不应混入 futures_1m
  - JSON 文件便于 Git 版本控制和未来开源
  - SQLite 也可以，但不急于引入第二个数据库
```

## 八、核心结论

1. **1m 数据 + 你的架构 = 已经是 SMC/ICT 练盘的甜蜜点**。不需要秒级数据。

2. **图表内语义标注是空白地带**。没有竞品做到"标注即数据，标注即统计"的闭环。

3. **垂直是护城河**。通用产品不可能为 SMC/ICT 硬编码 FVG/OB/SSL/Liquidity 概念，而这正是目标用户每天想的东西。

4. **用户是标注引擎，不是代码**。MVP 不需要自动识别 FVG，只需要让用户在图表上标注，然后自动统计。这比截图+Excel 已经好一百倍。

5. **Lightweight Charts 不需要理解 FVG**。LC 负责画，你的代码负责语义。两层解耦。

6. **数据成本优势巨大**。¥400 一次性 vs FXReplay $35/月 × 5年 = ¥15,120。

7. **产品定位从"回放练盘"升级为"操作系统验证"**——回放只是手段，验证 edge 才是目的。
