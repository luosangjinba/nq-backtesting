不做结构判断

4. BSL / SSL 是通过 swing 规则扫出来的
最核心的逻辑在 swing_records()，位置是 v2/scripts/scan_layer1_pda.py (line 438)。

它先看 SWING_RULES：

D: (1,1)
4H: (2,2)
1H: (3,3)
15M: (4,4)
意思是：不同周期，判断一个 swing high / low 需要看左右各几根 bar。

判断规则是：

is_high: 当前 bar 的 high 要大于右边所有比较 bar，并且大于等于左边所有比较 bar
is_low: 当前 bar 的 low 要小于右边所有比较 bar，并且小于等于左边所有比较 bar
这个“左边允许等于、右边必须严格更弱”的写法，是一个很细的 tie-break 设计，见 v2/scripts/scan_layer1_pda.py (line 446)。它的目的不是把一串 equal highs 全部丢掉，而是尽量保留最右边那个点，避免连续相等高低点导致候选全消失。

如果是 swing high，就生成 bsl；如果是 swing low，就生成 ssl。
confirm_time 用的是右侧窗口最后一根 bar 的 bucket_start，因为只有右边那几根走完，才算确认这个 swing。

后面还有一个补充逻辑也很重要，在 v2/scripts/scan_layer1_pda.py (line 489)：
如果两个相邻的局部极值价格完全一样，就额外把右边那个点再保留成候选，并打上 note="equal_extrema_right"。这说明作者很在意“等高 / 等低”这种 ICT 语境下常见的流动性点，不想被普通 swing 规则漏掉。

5. FVG 是标准三根 K 线规则
fvg_records() 在 v2/scripts/scan_layer1_pda.py (line 556)。

它按三根 bar a, b, c 扫描：

如果 c.low > a.high，形成 bullish FVG
如果 c.high < a.low，形成 bearish FVG
这里用的是很纯的三根 bar 缺口定义，没有加位移强弱、没有加 body 条件、没有做过滤。
锚点时间取中间那根 b.bucket_start，这很合理，因为 FVG 在 ICT 语境里通常是围绕中间那根 displacement candle 来识别的。

另外它只在 D/4H/1H 扫 FVG，不扫 15M，这点在主流程里能看到，见 v2/scripts/scan_layer1_pda.py (line 856)。

周二到周五生成 ndog

我建议把 EQH / EQL 当成 “关系型 PDA”，不是普通的 bsl/ssl 单点。它可以落在 pda_registry 里，但最好还要保留“它由哪些点组成”的成员关系，否则后面你会不知道这个 EQH/EQL 是哪几个 high/low 组成的。

1. 自动寻找规则
可以做，但我不建议第一版太聪明。第一版规则可以很机械：

输入候选：只从已有 point-like PDA 里找，比如 daily_high/daily_low/bsl/ssl/ict_midnight_day_high/ict_midnight_day_low，再加 pd_extremes 的 high/low。
EQH：找 side 为 high 的候选；EQL：找 side 为 low 的候选。
价格容差：例如 <= 1 tick 或 <= 2 ticks，NQ tick 是 0.25，所以可以先用 0.25 或 0.5。
最少触点：至少 2 个点。
时间间隔：不要把同一根 bar 或连续很近的重复点算成 EQH/EQL，至少隔一个 bucket 或隔一段时间。
输出：生成一条 pda_registry 记录，pda_type = 'eqh' / 'eql'，price 用 cluster 中位价或平均价，price_high/price_low 存 cluster 的上下边界。
自动生成时，我会把 source 设成类似 auto_eq_scan，并把 note 写入简短说明，比如 members=3 tolerance_ticks=1。

2. 手工补充
这个必须支持。原因很简单：EQH/EQL 很依赖交易者视觉判断，有些“等高/等低”不是数学上完全等价，但图上很明显。

现在 pda_review.html 手工新增只支持 bsl/ssl/fvg，API 里的 MANUAL_PDA_TYPES 也是这三个。要支持手工 EQH/EQL，至少要改：

price_lookup_api.py (line 27)：允许 eqh/eql
price_lookup_api.py (line 1163)：手工创建逻辑支持区间型或点型 EQH/EQL
v2/docs/pda_review.html (line 601)：手工新增下拉框加 eqh/eql
v2/schema/pda_registry.sql (line 1)：文档枚举补上 eqh/eql
手工补充时，我建议允许两种输入方式：只填一个代表价格，或者填 priceHigh/priceLow 表示一个等高/等低区域。EQH 本质是 high liquidity pool，EQL 本质是 low liquidity pool，所以不需要 direction。

3. 如何与 group 共存
这里是最重要的设计点。当前 reference_groups 的语义是：同一个时间点、同一个价格附近的多重身份共振。比如一个点同时是 D daily_high + 4H BSL + NY AM high。

但 EQH/EQL 的语义是：不同时间出现的多个相近价格点构成一组等高/等低流动性。

所以我不建议直接把 EQH/EQL 做成现有 reference_groups 的一种普通 group。它们不是同一种关系。

我更推荐这样共存：

reference_groups 继续表示“同一事件点的多重身份”。
eqh/eql 作为 pda_registry 里的 PDA 记录存在。
新增一个成员表，比如 pda_members 或 equal_liquidity_members，记录这条 EQH/EQL 由哪些 pda_id 或 pd_extreme ref 组成。
如果某个 EQH/EQL 的代表价格/时间也刚好和其他 PDA 共振，build_reference_groups.py 可以把这条 eqh/eql PDA 也纳入 group。
也就是说：EQH/EQL 可以参与 group，但不应该被 group 取代。

我会按这个顺序落地：

先扩展手工新增 eqh/eql，让你能在 pda_review.html 里补。
再加一个成员关系表，支持记录 EQH/EQL 由哪些点构成。
然后做自动扫描脚本，先输出建议，不直接污染主表。
最后把确认后的 EQH/EQL 纳入 reference_groups，让 Layer2 能引用它们。
我的判断是：先做“手工补充 + 可记录成员”，再做自动寻找。这样不会一上来被自动规则的误判拖住，也能让我们用你的真实标注习惯反过来校准自动规则。
