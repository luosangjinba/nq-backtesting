# 2026-04-17 分步实施方案

## 1. 这次讨论里已经可以确定的结论

这部分不再反复讨论，默认作为后续实施边界：

- 当前主目标是`快速研究`，不是伪实盘训练。
- 第一层 `PDA Registry` 继续走`纯机械、不过滤、不去重`路线。
- 第二层不再继续扩旧 `HTF bias`，主线转向独立的 `pendulum` 结构引擎。
- 研究方法改成`先记录事实，再从样本里长出预期`，而不是先写 bias 再去解释行情。
- `4H / 1D / 1W` PDA 主要提供高质量反应区，真正转向仍要依赖更低周期确认。
- `1H` 是日内核心机会来源层，`30m` 作为试验性人工补充层，不自动计算。
- `daily system` 后续只消费 `pendulum` 的结果，不维护 `pendulum` 本体。
- 所有新功能都要优先满足：`方便回看、方便修改、方便统计`。
- 当前 PDA 白名单先收口为：`bsl / ssl / fvg / nwog / ndog`
- `EQH / EQL` 当前不自动计算，先手工确定
- `30m` 作为试验性 timeframe 加入，但不自动计算，我事后会手工加，看看是否可行
- 数据必须允许手工修改，不把人工修正挡在流程外

## 2. 实施原则

- 小步慢跑：每次只推进一个最小闭环，不并行铺太多抽象层。
- 先样本后自动化：先让人能看、能记、能复盘，再考虑自动推断。
- 先事实后判断：优先落地“发生了什么”，延后“这意味着什么”。
- 先数据库后 UI：底层结构没稳定前，不投入重 UI。
- 每一步都带验收：没有可验证结果，就不进入下一步。
- 数据可手工更改：人工修正、补录、删除噪音、补充备注都应被系统允许，而不是视为例外。

## 3. 当前资源与现实起点

这里需要把“长期方向”和“当前开工点”分开看：

- `2005` 年至今的 `1m OHLC` 数据已经入 `DuckDB`
- 数据调用 API 已经可用
- `v1` 的每日盘面记录系统 `yaml_panel.html` 暂时保留
- `v2` 与 `pendulum` 先不作为第一落点

当前更现实的开工方式是：

- 先从现有 `yaml_panel.html` 周边起步
- 先把 `PDA 扫描 -> 人工整理 -> 反应研究 -> setup 归类` 这条短链跑通
- 等样本和口径稳定后，再决定哪些能力上收进 `v2`，哪些沉淀为 `pendulum`

## 4. 明确不在当前阶段做的事

- 不继续大规模扩旧 `HTF bias` 字段。
- 不把 `pseudo-live` 并入当前 V2 主流程。
- 不一开始就做完整自动 bias 判断器。
- 不一开始就做复杂 PDA 筛选器或跨周期去重器。
- 不一开始就把所有研究结果都塞回 daily 表单。
- 不把 `v2` 和 `pendulum` 当作当前第一阶段必须同步推进的前提。

## 5. 三层研究流程

结合补充说明，当前最合适的研究流程可以先固定成三层：

### 第一层：PDA 清洗层

目标：
先得到一套尽量干净、可维护的 `BSL / SSL / FVG / NDOG / NWOG` 数据库。

工作内容：

1. 自动筛查 `Daily / 4H / 1H` 的 PDA
2. 重点优先：
   - `BSL`
   - `SSL`
   - `FVG`
   - `NDOG`
   - `NWOG`
3. `30m` 只作为试验性人工补充层
   - 当前不自动计算
   - 只允许事后手工加，后续再评估是否值得保留
4. 人工去掉不重要的 `BSL / SSL` 杂音
5. 人工整理 `EQH / EQL`

说明：

- 第一层不是为了直接下结论
- 第一层是为了先把“地图”打干净
- 第一层输出的数据默认允许手工修正

### 第二层：全天反应研究层

目标：
研究价格如何寻找、sweep、尊重、忽略不同类型的 PDA。

工作内容：

1. 以 `0:00` 为分界，研究价格如何寻找并 sweep 不同种类的 `BSL / SSL`
2. 研究价格如何尊重不同周期的 `FVG`
3. 对每日走势进行归类
4. 以周为单位，对 5 个交易日的走势做归类
5. 重点研究 `9:30-11:00` 对 `BSL / SSL / FVG` 的反应
6. 研究失败样本：
   - 价格无反应
   - 价格只有小反应
   - 看似有反应但没有 follow-through

这一层有个很重要的边界：

- `PDA` 以及它引发的转折，是`全天`都需要记录的
- `订单研究`有时间窗，重点放在 `9:30-11:00`

### 第三层：Setup 归类与执行层

目标：
基于第二层样本，回到 `9:30-11:00` 研究可重复的入场机会。

工作内容：

1. 在 `9:30-11:00` 内寻找入场机会
2. 重点观察常用时间：
   - `9:30 Judas Swing`
   - `9:50 macro`
   - `Silver Bullet`
3. 重点观察常用 setup：
   - `OTE`
   - `2022`
   - `purge + OB`
4. 人工分类高质量 setup

说明：

- 第三层不是一开始就自动识别 setup
- 而是从第二层研究结果中慢慢长出 setup 分类

目标：把后面会反复打架的定义先固定到最小可用版本。

3. 固定 `reaction classification`
   - 第一版只保留最小枚举：

5. 固定时间边界

   - `9:30-11:00` 作为订单研究窗口
   - 全天 PDA 都记录，但订单研究先聚焦窗口内样本

6. 固定数据编辑原则
   - 扫描结果允许手工修改
   - 人工可以删除噪音、补录 `EQH / EQL`、补加 `30m` PDA、修正备注和分类

验收标准：

- 以上口径都写进文档或 schema 注释中。
- 后续新代码不再自己发明另一套命名。

### Phase 1. 补齐 Layer1 PDA 扫描闭环

目标：先把“地图层”做完整，但保持机械化，不在这一层引入主观筛选。

当前现实起点：

- 优先基于现有数据 API 和 `yaml_panel.html` 周边能力推进
- 不要求一上来就挂到完整 `v2` 主流程

本阶段建议顺序：

1. 检查并补齐 `scan_layer1_pda.py` 输出字段
   - 确保所有 PDA 至少有：
     - `instrument`
     - `timeframe`
     - `pda_type`
     - `price_low`
     - `price_high`
     - `anchor_time`
     - `confirm_time`
     - `status`

2. 按当前研究优先级补 PDA 类型
   - 优先保证：
     - `bsl`
     - `ssl`
     - `fvg`
     - `nwog`
     - `ndog`
   - 不把 `30m` 纳入自动扫描
   - `EQH / EQL` 不纳入自动扫描

3. 为 Layer1 建最小 smoke test
   - 每补一类 PDA，就加一个最小样例验证输出结构
   - 先测“能不能稳定扫出来”，不急着测“扫得聪不聪明”

4. 加一个人工清洗出口
   - 支持去掉明显不重要的 `BSL / SSL` 杂音
   - 支持补录或标记 `EQH / EQL`
   - 支持手工添加 `30m` PDA
   - 支持直接修改已有 PDA 数据

验收标准：

- 指定时间范围跑扫描时，能稳定写出当前重点 PDA 类型。
- 同一输入重复执行，结果数量和关键字段一致。
- 机械扫描与人工清洗边界清楚，没有混成一层黑箱。
- 手工修正后的数据能被保留，不会在下一次扫描时悄悄覆盖掉。

### Phase 2. 做一个极轻量的 PDA Review 视图

目标：不是做完整 UI，而是让人能快速看 Layer1 结果、做最小人工标注。

只做最小能力：

1. 查看某日附近的 PDA 列表
2. 按 timeframe / type 过滤
3. 手动标一个简单字段：
   - `watch_flag`
   - 或 `priority`
   - 或 `attention_reason`
4. 补一个很轻的人工整理能力：
   - 去掉噪音 `BSL / SSL`
   - 标记 `EQH / EQL`
   - 手工补加 `30m` PDA
   - 直接修改 PDA 字段

这一阶段只解决一个问题：
`从“扫出来很多点”到“我今天重点看哪些点”之间，要有一个很轻的人工筛选层。`

验收标准：

- 人能在几分钟内完成“浏览 + 标重点 PDA”。
- 标注结果可以保存并复用到下一层复盘，不需要每次重来。

### Phase 3. 先做 Reaction Review，不急着做趋势引擎

目标：先把“价格到了 PDA 后发生了什么”结构化下来。

原因：

- 这是当前讨论中最确定、最直接产生研究价值的一层。
- 它比直接做自动 bias 更稳，也更符合“先事实后判断”。

第一版只记录：

- `pda_id`
- `touch_time`
- `reaction_type`
- `reaction_note`
- `follow_through_result`
- `opportunity_window_hit`（是否落在 9:30-11:00）
- `day_bucket`（按 `0:00` 分日）

建议第一版先只研究：

- 来源于 `1H / 4H / D` 的 PDA
- 全天都记录 PDA 反应
- 重点单独统计 `9:30-11:00`
- 只记首个主要反应，不追求全天所有细节
- 明确保留失败样本：
  - `no_reaction`
  - `small_reaction`
  - `reaction_without_follow_through`

验收标准：

- 能从一个交易日快速生成若干条“PDA 反应样本”。
- 一周样本拉出来后，已经可以按 `timeframe / reaction_type / opportunity_window_hit` 做简单统计。
- 能按日和按周做基础归类。

### Phase 4. 从反应研究中长出 Day Type / Week Type

目标：先做“走势归类”，再做“入场模板”。

本阶段只做两件事：

1. 对每日走势做人工归类
2. 对一周 5 个交易日做周级归类

原因：

- 如果没有 day type / week type，setup 很容易碎片化
- 先做走势归类，更容易看清不同 PDA 在不同环境里的作用

验收标准：

- 至少有一套简单可复用的日级分类口径
- 能对连续一周样本给出周级归类

### Phase 5. 先做人类可用的 Setup Catalog

目标：把第二层样本里反复出现的高质量机会归成少量 setup。

本阶段重点不是自动识别，而是人工分类：

- `OTE`
- `2022`
- `purge + OB`
- `9:30 Judas Swing`
- `9:50 macro`
- `Silver Bullet`

验收标准：

- 能从样本中持续归档“高质量 setup”
- 每个 setup 至少能附带：
  - 触发 PDA 类型
  - 主要时间窗
  - 常见确认方式
  - 失败特征

### Phase 6. 再启动 Pendulum Phase 1，只做点和状态，不做复杂推理

目标：把 `pendulum` 作为独立上游系统跑起来，但第一版只做最小状态管理。

本阶段顺序：

1. 先落数据库 schema
   - 以 `PENDULUM_SCHEMA.sql` 为准
   - 先确保三类实体能稳定存：
     - `pendulum_snapshots`
     - `pendulum_events`
     - `pendulum_structure_points`

2. 先做 `candidate point -> 人工确认 -> 入库`
   - 默认沿用当前 candidate 规则
   - 先只支持 `daily` 或 `1H`，不要一开始全周期铺开

3. 先输出最小状态快照
   - `structural_bias`
   - `structure_status`
   - `phase`
   - `confirmation_state`
   - `protected_high`
   - `protected_low`

注意：

- 这一阶段先不要追求“自动判断对不对”
- 重点是“结构状态能否连续维护”

验收标准：

- 给定一段历史 bars，能够形成连续的 point 和 snapshot 记录。
- 对同一历史区间重复跑，结构点和状态输出基本稳定。

### Phase 7. 把 Pendulum 以薄引用方式接入 Daily

目标：daily 不再自己重写 HTF 故事，而是消费上游结论。

只做最薄的一层：

- 在 daily 中加入 `pendulum_ref`
- 引入：
  - `source_timeframe`
  - `pendulum_snapshot_id`
  - `structural_bias`
  - `phase`
  - `confirmation_state`
  - `protected_high`
  - `protected_low`

这一阶段不要做：

- 不在 daily 里复制完整 pendulum 状态机
- 不再继续扩 daily 里的旧 `HTF bias` 主观字段

验收标准：

- daily 可以引用某个 `pendulum snapshot`
- 用户在 daily 页面能看见上游结构结论，但不需要手填一遍

### Phase 8. 回头补研究增强项，而不是继续加主观字段

目标：等前面 5 个阶段都能跑通，再补增强层。

优先顺序建议：

1. `swing` 研究增强
   - `mae_time`
   - `mfe_time`
   - `beyond_swing`
   - `retracement_after_internal`

2. `bias_updates[]`
   - 用于记录结构判断何时改变、因何改变

3. `sweep / break` 量化字段
   - `daily_close_side`
   - `next_daily_close_side`
   - `penetration_atr_pct`
   - `body_beyond_pct`

说明：

- 这些都属于“研究增强层”
- 必须建立在前面的基础链路已经稳定之上

## 7. 每个阶段的测试要求

为了符合“边测试，边改进，边迭代”，每一阶段都只做对应层的测试：

- Phase 1 测扫描稳定性，不测主观有效性
- Phase 2 测人工筛选流程是否顺手，不测最终收益
- Phase 3 测反应记录是否可统计，不测自动预测能力
- Phase 4 测日级/周级归类是否稳定，不测交易胜率
- Phase 5 测 setup 分类是否可复用，不测自动识别能力
- Phase 6 测结构状态是否连续一致，不测 bias 胜率
- Phase 7 测引用链路是否通，不测整套交易闭环

一句话：
`每一阶段只验证这一阶段承诺解决的问题。`

## 8. 建议的最近两周执行节奏

如果按“小步慢跑”推进，建议这样排：

第 1 周：

1. 完成 Phase 0
2. 优先补出 `bsl / ssl / fvg / nwog / ndog` 中最缺的一项
3. 给 Layer1 增加最小 smoke test
4. 做出可浏览、可人工清洗的 PDA Review 初版

第 2 周：

1. 把 PDA Review 标注结果接到 Reaction Review
2. 跑 3 到 5 个交易日样本
3. 根据样本修正 reaction 分类和记录字段
4. 尝试做第一版 day type 归类

## 9. 当前最推荐的落地起点

如果按现在的资源和约束开工，最推荐的起点是：

1. 继续沿用现有 `yaml_panel.html`
2. 在其周边补 `PDA 扫描 + 人工清洗`
3. 立刻衔接 `Reaction Review`
4. 从反应样本里长出 `day type / week type / setup catalog`
5. 最后再考虑把稳定部分迁移到 `v2 / pendulum`

原因很简单：

- 这条链最短
- 最容易快速产出样本
- 最符合“先事实、后结构、再判断”
- 也更符合当前已经具备的数据和工具条件
- 做完以后再反推 `v2 / pendulum`，理解会更稳

## 10. 一句话总纲

先用现有系统把`地图`做干净，再把`全天反应`记清楚，再从样本里长出`day type / setup`，最后才把稳定能力上收进 `v2 / pendulum`。

这条顺序比“先造一个大而全的 bias 系统”更慢一点，但更稳，也更容易持续迭代。

## 11. Phase 0 硬口径定义

这一节作为当前阶段的直接实施口径，后续代码、表结构、页面字段都优先对齐这里。

### 11.1 PDA 类型白名单

当前只允许以下 PDA 类型进入主流程：

- `bsl`
- `ssl`
- `fvg`
- `nwog`
- `ndog`

说明：

- 这是一版收口后的最小白名单
- 当前先不要把其他类型混进主流程
- 后续如果要扩类型，必须单独讨论并更新本文档

### 11.2 EQH / EQL 规则

当前规则：

- `EQH / EQL` 不自动计算
- `EQH / EQL` 只允许手工确定
- 手工确定后的 `EQH / EQL` 可以作为研究辅助信息保留
- 但它们不属于当前自动扫描白名单的一部分

### 11.3 Timeframe 角色定义

当前只使用以下 timeframe：

- `D`
- `4H`
- `1H`
- `30m`

角色定义如下：

- `D`
  - 框架层
  - 用于提供更高一级的背景和关键 PDA

- `4H`
  - 路径层
  - 用于观察中等尺度的价格路径和关键反应区

- `1H`
  - 日内核心机会来源层
  - 当前日内研究重点优先放在 `1H` 及以上

- `30m`
  - 试验性人工补充层
  - 当前不自动计算
  - 只允许事后手工添加
  - 加入它的目的，是观察它是否真的提供稳定研究价值

### 11.4 自动扫描范围

当前自动扫描只覆盖：

- `D / 4H / 1H`
- PDA 类型仅限：
  - `bsl`
  - `ssl`
  - `fvg`
  - `nwog`
  - `ndog`

当前明确不自动做：

- 不自动计算 `30m`
- 不自动计算 `EQH / EQL`
- 不自动扩展到更多 PDA 类型

### 11.5 手工编辑原则

当前系统必须支持手工编辑，且手工编辑不是例外，而是主流程的一部分。

允许的手工操作包括：

- 删除明显不重要的 `bsl / ssl` 杂音
- 补录 `EQH / EQL`
- 手工添加 `30m` PDA
- 修改 PDA 的备注、标签、分类
- 修正明显错误的价格、时间、状态

实现原则：

- 自动扫描结果必须允许人工修订
- 人工修订结果必须能保存
- 后续重新扫描时，不能悄悄覆盖人工修订
- 如果自动结果与人工修订冲突，必须有清晰的覆盖策略

### 11.6 当前推荐的最小 PDA 字段

无论底层最终落在页面、YAML、CSV 还是数据库，当前每条 PDA 最少应支持这些字段：

- `pda_id`
- `trade_date`
- `timeframe`
- `pda_type`
- `price_low`
- `price_high`
- `anchor_time`
- `confirm_time`
- `source`
- `status`
- `manual_added`
- `manual_edited`
- `note`

字段建议解释：

- `pda_id`
  - 唯一标识

- `trade_date`
  - 当前研究归属日期
  - 先按 `0:00` 分日

- `timeframe`
  - 只允许：`D / 4H / 1H / 30m`

- `pda_type`
  - 只允许：`bsl / ssl / fvg / nwog / ndog`

- `price_low`
  - PDA 下沿价格

- `price_high`
  - PDA 上沿价格

- `anchor_time`
  - 该 PDA 的主记录时间
  - 不同 PDA 类型的含义不同，下面单独定义

- `confirm_time`
  - 该 PDA 被确认成立的时间
  - 只在确实有“确认时间”语义时填写
  - 没有单独确认时间的 PDA 可以留空

- `source`
  - 建议先只允许：
    - `auto_scan`
    - `manual_add`
    - `manual_eqh_eql`

- `status`
  - 建议第一版只允许：
    - `active`
    - `archived`
    - `deleted_by_review`

- `manual_added`
  - 布尔值
  - 标记是否为手工新增

- `manual_edited`
  - 布尔值
  - 标记是否在自动结果基础上被人工改动过

- `note`
  - 自由备注

### 11.6.1 PDA 时间记录总原则

所有 K 线时间统一按 `K 线开始时间` 记录。

例如：

- `2:00` 开始的 `4H` K 线，时间记录为 `2:00`
- 不记录该根 K 线结束时刻，例如 `5:59`

这一条对自动扫描和手工录入都同时生效。

### 11.6.2 BSL / SSL 记录逻辑

`bsl / ssl` 的记录逻辑与 `fvg / nwog / ndog` 不同，必须单独处理。

建议记录：

- `price_low`
- `price_high`
- `anchor_time`
- `confirm_time`

字段解释：

- `price_low / price_high`
  - 对于 `bsl / ssl`，这里记录的是“当根 K 线极值点”的价格信息
  - 如果底层实现更细，也可以额外拆出 `extreme_price`
  - 但第一版至少要保证能明确还原该极值点

- `anchor_time`
  - 记录“当根 K 线的时间”
  - 也就是该极值所在 K 线的开始时间

- `confirm_time`
  - 记录“确认 K 线的时间”
  - 按照自动搜索 `bsl / ssl` 的标准记录

一句话：

- `bsl / ssl` 要同时保留“极值发生在哪根 K 线”与“哪根 K 线完成确认”这两个时间
- `bsl / ssl` 的候选扫描遇到连续相邻等高 / 等低时，统一只保留最右边那个点；这条规则直接在候选识别阶段生效，而不是事后再去重

### 11.6.3 FVG 记录逻辑

`fvg` 的记录逻辑如下：

- 记录 3 根 K 线中第 2 根 K 线的时间
- 不单独记录确认时间
- 记录 `fvg` 的高低点

字段映射建议：

- `anchor_time`
  - 记录第 2 根 K 线的开始时间

- `confirm_time`
  - 留空
  - 因为确认时间天然就是第 3 根 K 线，不需要额外存一列去重复表达

- `price_low / price_high`
  - 记录该 `fvg` 的价格区间上下沿

### 11.6.4 NWOG / NDOG 记录逻辑

`nwog / ndog` 的记录逻辑如下：

- `gap` 的形成需要两根 K 线确认
- 核心是前一段收盘价与后一段开盘价之间的缺口
- 常见情况是：
  - `16:59` 收盘价
  - `18:00` 开盘价
- 个别特殊情况：
  - 收盘时间不是 `16:59`
  - 可能是 `13:14`
  - 也可能是其他时间
- 这些特殊情况也必须记录

字段映射建议：

- `price_low / price_high`
  - 记录构成 `gap` 的两个价格
  - 也就是前一段收盘价与后一段开盘价对应形成的区间

- `anchor_time`
  - 记录后一段开盘对应那根 K 线的开始时间
  - 因为 `gap` 的识别落点最终是新一段开始时被确认看见

- `confirm_time`
  - 留空
  - 因为 `nwog / ndog` 的形成本身就是由这两端价格共同定义，不需要再另加一根确认 K 线

补充建议：

如果实现时允许扩字段，`nwog / ndog` 最好额外保留：

- `prev_close_time`
- `prev_close_price`
- `next_open_time`
- `next_open_price`

原因：

- 这样可以明确保留特殊收盘时刻
- 对 `16:59 -> 18:00` 以外的异常或特殊 session 更友好
- 也方便后续回查数据源是否存在 session 例外

当前实现约束：

- 扫描脚本当前把 `nwog / ndog` 作为 `D` 层 session gap 输出
- 也就是它们当前不会在 `4H / 1H` 下重复生成
- 自动扫描时：
  - 起点按 `16:59 close` 查询
  - 允许 `fallback prev`
  - 因此会记录真实命中的特殊收盘时刻
  - 终点按 `18:00 open` 查询

### 11.7 当前推荐的最小 Review 字段

为了让第一轮研究尽快跑起来，PDA Review 层建议至少支持这些字段：

- `watch_flag`
- `review_action`
- `review_note`

推荐枚举：

- `watch_flag`
  - `watch`
  - `ignore`

- `review_action`
  - `keep`
  - `drop_noise`
  - `mark_eqh`
  - `mark_eql`
  - `add_30m`
  - `edit_existing`

说明：

- 第一版 review 不需要太复杂
- 先能完成“保留 / 去噪 / 补充 / 修改”这四类动作就够了

### 11.8 当前推荐的最小 Reaction 字段

Reaction Review 第一版建议至少支持：

- `pda_id`
- `day_bucket`
- `touch_time`
- `reaction_type`
- `opportunity_window_hit`
- `follow_through_result`
- `reaction_note`

推荐枚举：

- `reaction_type`
  - `reject`
  - `break_and_hold`
  - `sweep_and_reverse`
  - `no_clear_reaction`

- `opportunity_window_hit`
  - `yes`
  - `no`

- `follow_through_result`
  - `none`
  - `small_move`
  - `clear_move`
  - `failed_after_reaction`

说明：

- 第一版先保证能做横向统计
- 先不要把 reaction 分类做得过细

### 11.9 当前推荐的覆盖策略

为了避免“自动扫描一跑就把人工修正洗掉”，当前建议先采用最保守策略：

- 自动扫描只负责新增和更新“自动层原始结果”
- 人工 review 层单独保存
- 页面展示时，以“自动层 + 人工修正层合成结果”为准

一句话：

- `自动层保留原始扫描结果`
- `人工层保留清洗和补录结果`
- `展示层输出最终可研究视图`

这样做的好处：

- 不容易丢手工劳动
- 后续想回溯“原始扫描长什么样”也更容易
- 未来如果升级扫描逻辑，能更清楚比较自动结果与人工修正的差异

## 12. Phase 1 Schema Draft

这一节不是最终数据库定稿，而是当前阶段可直接照着实现的最小 schema 草案。

设计目标只有 3 个：

- 能保存自动扫描原始结果
- 能保存人工清洗和补录结果
- 能稳定产出“最终可研究视图”

### 12.1 推荐分层

当前建议至少拆成 3 层：

1. `pda_auto_scan`
   - 保存自动扫描原始结果

2. `pda_manual_review`
   - 保存人工清洗、补录、修正动作

3. `pda_final_view`
   - 页面或查询层使用的最终结果视图

一句话：

- 自动层不直接覆盖人工层
- 人工层不直接抹掉自动层
- 最终展示由两层合成

### 12.2 表一：`pda_auto_scan`

用途：

- 存放自动扫描出来的原始 PDA
- 只记录机器结果，不承担人工解释

推荐字段：

- `id`
- `scan_batch_id`
- `instrument`
- `trade_date`
- `timeframe`
- `pda_type`
- `anchor_time`
- `confirm_time`
- `price_low`
- `price_high`
- `source`
- `status`
- `created_at`
- `updated_at`

字段建议：

- `id`
  - 主键

- `scan_batch_id`
  - 一次扫描任务的批次号
  - 方便比较不同扫描版本输出差异

- `instrument`
  - 例如 `NQ`

- `trade_date`
  - 研究归属日期
  - 按 `0:00` 分日

- `timeframe`
  - 只允许：
    - `D`
    - `4H`
    - `1H`

- `pda_type`
  - 只允许：
    - `bsl`
    - `ssl`
    - `fvg`
    - `nwog`
    - `ndog`

- `anchor_time`
  - 主记录时间
  - 各 PDA 类型语义按 `11.6.x` 定义执行

- `confirm_time`
  - 仅在有确认时间语义时填写

- `price_low / price_high`
  - PDA 对应价格区间

- `source`
  - 建议固定为：
    - `auto_scan`

- `status`
  - 建议第一版固定为：
    - `active`
    - `archived`

说明：

- `30m`
  - 不进入这张表
- `EQH / EQL`
  - 不进入这张表

### 12.3 表二：`pda_manual_review`

用途：

- 保存人工对 PDA 的处理动作
- 包括去噪、修订、补录、标记 `EQH / EQL`、手工添加 `30m`

推荐字段：

- `id`
- `target_type`
- `target_id`
- `instrument`
- `trade_date`
- `timeframe`
- `pda_type`
- `review_action`
- `watch_flag`
- `anchor_time`
- `confirm_time`
- `price_low`
- `price_high`
- `manual_tag`
- `review_note`
- `reviewer`
- `created_at`
- `updated_at`

字段建议：

- `target_type`
  - 建议允许：
    - `auto_scan_row`
    - `manual_entry`

- `target_id`
  - 如果本条 review 是针对自动扫描结果，就指向 `pda_auto_scan.id`
  - 如果本条是纯手工新增，可以为空

- `timeframe`
  - 允许：
    - `D`
    - `4H`
    - `1H`
    - `30m`

- `pda_type`
  - 当前仍只允许：
    - `bsl`
    - `ssl`
    - `fvg`
    - `nwog`
    - `ndog`
  - `EQH / EQL` 不建议直接塞进 `pda_type`
  - 更适合作为 `manual_tag`

- `review_action`
  - 建议允许：
    - `keep`
    - `drop_noise`
    - `edit_existing`
    - `manual_add`
    - `mark_eqh`
    - `mark_eql`

- `watch_flag`
  - 建议允许：
    - `watch`
    - `ignore`

- `anchor_time / confirm_time / price_low / price_high`
  - 当 review 动作涉及修正或补录时，保存修正后的值

- `manual_tag`
  - 建议第一版允许：
    - `eqh`
    - `eql`
    - `trial_30m`
    - `none`

说明：

- `manual_add`
  - 用于纯手工补录
  - 例如手工添加 `30m` PDA

- `mark_eqh / mark_eql`
  - 是人工附加标签
  - 不代表自动扫描层原本就识别到了一个新的 PDA 类型

### 12.4 视图三：`pda_final_view`

用途：

- 产出最终给页面和研究流程使用的 PDA 结果
- 这是一层合成视图，不一定必须真实建表

建议输出字段：

- `final_id`
- `source_row_id`
- `instrument`
- `trade_date`
- `timeframe`
- `pda_type`
- `anchor_time`
- `confirm_time`
- `price_low`
- `price_high`
- `watch_flag`
- `manual_tag`
- `is_manual`
- `is_edited`
- `is_dropped`
- `note`

合成逻辑建议：

1. 如果自动扫描结果没有人工 review
   - 直接展示自动结果

2. 如果人工 review 是 `drop_noise`
   - 最终视图标记 `is_dropped = true`
   - 默认前端可隐藏

3. 如果人工 review 是 `edit_existing`
   - 优先展示人工修订后的字段
   - 同时保留与自动层的关联

4. 如果人工 review 是 `manual_add`
   - 直接作为最终结果的一部分输出

5. 如果人工 review 带有 `eqh / eql / trial_30m`
   - 这些标签在最终视图中一并暴露

### 12.5 当前推荐的唯一性策略

第一版不要追求太复杂的严格唯一约束，但建议至少有以下思路：

- 自动扫描层：
  - 可以考虑用下面这些字段近似唯一：
    - `instrument`
    - `trade_date`
    - `timeframe`
    - `pda_type`
    - `anchor_time`
    - `price_low`
    - `price_high`

- 人工层：
  - 不强行去重
  - 允许保留编辑历史
  - 但页面默认只取每个目标的最新有效 review

### 12.6 当前推荐的最小索引思路

如果后面落到数据库，第一版建议优先建这些索引：

- `pda_auto_scan(instrument, trade_date)`
- `pda_auto_scan(timeframe, pda_type)`
- `pda_manual_review(target_id)`
- `pda_manual_review(instrument, trade_date)`

原因：

- 大多数查询都会先按日期和品种过滤
- Review 层最常见动作是查某条自动结果有没有被人工处理过

### 12.7 当前推荐的导入导出策略

考虑到当前阶段需要高频人工修订，建议导入导出都尽量简单：

- 自动扫描结果可以导出成 `CSV`
- 人工 review 结果也可以单独导出成 `CSV`
- 页面展示时再做合并

这样做的好处：

- 便于快速检查
- 便于手工修正
- 暂时不被数据库实现细节卡住
