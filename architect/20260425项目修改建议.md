 2. layer2_recorder 改造方向（核心）
    
    把当前实现拆成三块来看：
    
    
    [A] Context 加载       拉取 5 个 timeframe 的 pda_registry + pd_extremes
                           + reference_groups（自动同价多重身份组）
    [B] PDA / Group / 
        Extreme 候选选择   左栏三个 tab，点击"添加"塞进当前 path 的 refs[]
    [C] Structure Path 
        元数据 + YAML 导出  ID/方向/时间区间/main_actions/etc
    
    
    你说的"做几个就把自己弄迷糊"，根因在 [B]：
    
    - 5 个 timeframe × 多种 pda_type，单日左侧候选量极大（光 15M bsl/ssl 全表就 64K 条）
    - reference_groups 自动同价位分组本意是减负，但它把"什么算同一关键点"的判断权交给 schema，形成了一个隐藏决策层
    - 你在筛 PDA 时同时还要给 path 编时间区间、main_action ref，注意力切换成本太高
    
    改造建议（保持你的"行情段录 1H"的本意）：
    
    
    保留：[A] 的"按日拉取后端数据"能力（contextual reference）
    保留：[C] structure path 元数据表单 + YAML 导出
    改造：[B] 候选选择 → 改成"手工录入 PDA"
    
    具体落地：
    ─ 删除"PDA / Groups / Session Extremes"三 tab 及相关 list 渲染
    ─ 新增一个 manual_pda 表单：
        timeframe / pda_type / direction / event_time / price (or high/low)
        起始原因 / 终止原因 / note
    ─ 录完直接挂在当前 structure path 下
    ─ 当前已加载的 v2 数据降级为"对照面板（read-only）"：
        沿用现有 GET /v2/pda_records，仅作为右侧对照查询，不能直接添加为 ref
    ─ 每条 manual_pda 提交保存时（或导出 YAML 时），调用比对：
        在 v2_research.duckdb 中按
            instrument / 同 timeframe / event_time ±1bar / 价位 ±tick
        搜索是否有命中
        命中 → 记录 matched_pda_id + match_score
        未命中 → 标记为 manual_only（这就是你想要的"手工 vs 自动"差集）
    ─ YAML 增加 reconciliation 块：
        matched_auto: [...]      # 这条人工PDA被自动扫描捕获了
        manual_only: [...]       # 自动扫描漏掉的
        auto_only_in_window: [...] # 自动扫到但你没标注重要的（用于盯漏）
    
    
    后端最小新接口（推荐 1 个就够）：

GET /v2/pda_match
      ?instrument=NQ&timeframe=1H&pda_type=bsl
      &event_time=2012-01-10 10:04:00&price=2378.25
      &time_tolerance_bars=1&price_tolerance_ticks=2
    → 返回若干候选 + 命中等级

这个接口的 SQL 复用 query_v2_pda_records 的过滤逻辑，工作量很小。

数据写在哪：    

方案 A（推荐，开销最小）：YAML 是真相之源
  - 手工 PDA 不入 duckdb，只随 structure path YAML 一起存盘
  - 比对结果也只写进 YAML
  - 优点：录入完全无副作用，迷糊了直接改 YAML
  - 缺点：跨样本统计时要重读所有 YAML

方案 B：手工 PDA 也进 pda_registry（manual_added=true）
  - 走现有 /v2/pda_manual_add 接口
  - 优点：统计统一在 duckdb 里
  - 缺点：又把"权威库"和"探索性手工"混在一起，
         你之前迷糊的根源就是这里

我建议先走方案 A。等录满 30 条左右、口径稳定，再决定是否回流到 duckdb。

3. 代码层面的问题

按"实际让你头疼"的程度排序，不是按 OOP 美学：

(a) price_lookup_api.py 单文件 2049 行 / 60+ 函数
- 校验函数（validate_*）30+ 个，全部贴墙铺平
- DuckDB 访问、HTTP handler、multipart 解析、CORS、还原点逻辑混在一起
- 没有依赖注入：db_path / v2_db_path / image_root 都通过 RequestHandler 类属性注入，重启 API 才能切库
- 影响：以后想加一个 /v2/pda_match，要在两个 do_GET 长 if 链里再加一个 if parsed.path == ...，并且被迫读懂相邻 200 行代码

最小手术建议（不重写）：

price_lookup_api/
├── main.py        参数解析+启动
├── server.py          BaseHTTPRequestHandler + 路由表（dict[str, callable]）
├── db.py              open_db / ensure_*
├── queries/
│   ├── price.py
│   ├── htf.py
│   ├── pda.py
│   ├── pd_extremes.py
│   ├── reference_groups.py
│   └── restore_points.py
└── validators.py

路由表化以后，加新接口=加一行 dict + 一个函数，不需要改大 if-else。



(b) layer2_recorder.html 是 1451 行手写 vanilla JS
- 与 pda_review.html 完全独立，两套 state、两套渲染、两套样式，CSS 还都几乎一样
- localStorage key layer2_recorder_draft_v1 没有版本迁移
- loadDraft() 直接 Object.assign(state, draft)，schema 一变就静默坏掉
- 影响：你这次想改 schema（去掉自动 PDA、加手工 PDA），代码改动估计要碰 30+ 处

建议：既然 [B] 候选块整个要换，我推荐直接重写一个精简版 layer2_recorder_v2.html，原文件保留作 reference。新版控制在 800 行内：

┌── topbar：date / instrument / API base / load
├── left：当前 path 的 manual PDA 表单 + 列表
├── center：path 元数据表单（保留现有所有字段）
└── right：YAML 预览 + 对照面板（read-only：v2 库当日相邻 PDA）

- pda_events 至今 0 行，schema 还在

- reference_groups 是为 layer2 自动找关键点而生的中间层

如果接受新方向（layer2 改成手工录入），reference_groups 就从"主路径"降为"对照参考"，build_reference_groups.py 不再是必跑步骤。
