# 全量扫描前抽查清单

## 1. 目标

在全量扫描前，先用一套固定抽查流程确认以下几件事：

- 字段语义是否正确
- 不同 `pda_type` 的记录逻辑是否符合定义
- 不同 `timeframe` 下时间和价格是否对得上
- `ndog / nwog` 的特殊收盘时刻是否被真实记录
- 当前扫描结果是否已经稳定到可以全量跑

## 2. 抽查原则

- 先扫小样本到临时库，不直接污染正式库
- 页面核对和 SQL 核对同时做
- 每一类都看“正常样本”和“边界样本”
- 抽查通过后，再考虑全量扫描

## 3. 推荐抽查顺序

### Step 1. 先跑一个临时库

建议先扫描一个较小但有代表性的时间段到临时库，例如：

- `2012-01-03` 到 `2012-01-31`
- 或者任意你熟悉、方便肉眼复盘的一段

示例命令：

```bash
python3 v2/scripts/scan_layer1_pda.py \
  --source-db trading_data.duckdb \
  --target-db /tmp/v2_research_check.duckdb \
  --instrument NQ \
  --timeframes D,4H,1H \
  --date-from 2012-01-03 \
  --date-to 2012-01-31 \
  --replace
```

### Step 2. 按类型抽查

每种类型先抽 10 条：

- `bsl`
- `ssl`
- `fvg`
- `ndog`
- `nwog`

重点看：

- `anchor_time`
- `confirm_time`
- `price_low / price_high`
- `prev_close_time / next_open_time`

### Step 3. 按 timeframe 抽查

分别抽查：

- `D`
- `4H`
- `1H`

重点看：

- K 线时间是否都按开始时间记录
- `bsl / ssl` 的确认时间是否合理
- `fvg` 的 `anchor_time` 是否真是第 2 根 K 线

### Step 4. 抽查 gap 特殊样本

重点核查：

- `ndog / nwog` 是否都落在 `anchor_time = 18:00`
- `prev_close_time` 是否可能不是 `16:59`
- 特殊时刻是否真的保留下来

### Step 5. 按历史阶段抽查

至少分 3 段：

1. 早期
   - 例如 `2008-2009`

2. 中期
   - 例如 `2015-2018`

3. 近期
   - 例如 `2024-2025`

目的是检查：

- 不同年份的数据缺口情况是否不同
- 扫描逻辑是否对全历史都稳定

## 4. 页面抽查清单

打开 `pda_review.html` 后，建议每条样本至少确认这些点：

### 对 `bsl / ssl`

- 焦点 bar 是否就是极值所在 bar
- 左右邻居是否符合当前 `left/right` 规则
- `confirm_time` 是否是确认 bar 的开始时间
- `price` 是否等于该极值

### 对 `fvg`

- 焦点时间是否是第 2 根 K 线
- `confirm_time` 是否为空
- `price_low / price_high` 是否真是 gap 上下沿

### 对 `ndog / nwog`

- 焦点 bar 是否是 `18:00` 的开盘 bar
- 详情区是否显示：
  - `Prev Close Ts`
  - `Next Open Ts`
  - `Gap Window`
- `prev_close_time` 是否保留了真实命中的特殊收盘时刻

## 5. SQL 抽查清单

以下 SQL 默认针对临时库：

- `/tmp/v2_research_check.duckdb`

可以这样进入：

```bash
python3 - <<'PY'
import duckdb
conn = duckdb.connect('/tmp/v2_research_check.duckdb')
print('connected')
PY
```

### 5.1 先看整体数量

```sql
select pda_type, count(*)
from pda_registry
group by 1
order by 1;
```

```sql
select timeframe, pda_type, count(*)
from pda_registry
group by 1, 2
order by 1, 2;
```

### 5.2 抽查 `bsl`

```sql
select
  pda_id,
  trade_date,
  timeframe,
  anchor_time,
  confirm_time,
  price,
  price_low,
  price_high
from pda_registry
where pda_type = 'bsl'
order by trade_date, anchor_time
limit 10;
```

### 5.3 抽查 `ssl`

```sql
select
  pda_id,
  trade_date,
  timeframe,
  anchor_time,
  confirm_time,
  price,
  price_low,
  price_high
from pda_registry
where pda_type = 'ssl'
order by trade_date, anchor_time
limit 10;
```

### 5.4 抽查 `fvg`

```sql
select
  pda_id,
  trade_date,
  timeframe,
  anchor_time,
  confirm_time,
  direction,
  price_low,
  price_high,
  price_ce
from pda_registry
where pda_type = 'fvg'
order by trade_date, anchor_time
limit 10;
```

### 5.5 抽查 `ndog / nwog`

```sql
select
  pda_id,
  pda_type,
  trade_date,
  anchor_time,
  prev_close_time,
  prev_close_price,
  next_open_time,
  next_open_price,
  price_low,
  price_high,
  direction
from pda_registry
where pda_type in ('ndog', 'nwog')
order by trade_date, pda_type;
```

### 5.6 专门查“特殊收盘时刻”

这条最重要：

```sql
select
  pda_id,
  pda_type,
  trade_date,
  prev_close_time,
  next_open_time,
  prev_close_price,
  next_open_price
from pda_registry
where pda_type in ('ndog', 'nwog')
  and strftime(prev_close_time, '%H:%M') <> '16:59'
order by trade_date, pda_type;
```

如果这里能查出记录，说明“特殊收盘时刻保留”已经生效。

### 5.7 检查 `fvg` 是否错误带了确认时间

```sql
select
  count(*) as bad_fvg_rows
from pda_registry
where pda_type = 'fvg'
  and confirm_time is not null;
```

期待结果：

- `0`

### 5.8 检查 `bsl / ssl` 是否缺确认时间

```sql
select
  pda_type,
  count(*) as missing_confirm
from pda_registry
where pda_type in ('bsl', 'ssl')
  and confirm_time is null
group by 1;
```

期待结果：

- 尽量为 `0`

### 5.9 检查 `ndog / nwog` 是否错误带了确认时间

```sql
select
  pda_type,
  count(*) as bad_gap_confirm
from pda_registry
where pda_type in ('ndog', 'nwog')
  and confirm_time is not null
group by 1;
```

期待结果：

- `0`

## 6. 一键检查脚本

如果不想手工逐条执行 SQL，可以直接跑：

```bash
python3 v2/scripts/check_pda_scan.py --db /tmp/v2_research_check.duckdb
```

可选参数：

```bash
python3 v2/scripts/check_pda_scan.py \
  --db /tmp/v2_research_check.duckdb \
  --sample-limit 15
```

脚本会输出：

- `Counts By PDA Type`
- `Counts By Timeframe And Type`
- `Sanity Checks`
- `Gap Special Close Times`
- `Sample BSL`
- `Sample SSL`
- `Sample FVG`
- `Sample NDOG/NWOG`

## 7. 三段历史抽查模板

建议每段都重复一次“数量 + 类型 + gap 特殊时刻”检查。

### 段 1

- `2008-01-01` 到 `2008-03-31`

### 段 2

- `2015-01-01` 到 `2015-03-31`

### 段 3

- `2024-01-01` 到 `2024-03-31`

## 8. 通过标准

如果以下条件都满足，就可以认为“适合全量扫描”：

- `bsl / ssl / fvg / ndog / nwog` 都能稳定产出
- `bsl / ssl` 的 `confirm_time` 语义正确
- `fvg` 的 `anchor_time` 语义正确，且 `confirm_time` 为空
- `ndog / nwog` 的 `prev_close_time / next_open_time` 语义正确
- 特殊收盘时刻被保留
- 不同历史阶段抽查结果没有出现明显口径漂移

## 9. 不通过时怎么处理

如果抽查不通过，不要直接全量跑。

建议先判断问题属于哪类：

1. 字段语义错
   - 先修扫描逻辑

2. 少量脏数据
   - 先确认是不是源数据问题

3. 某个 `pda_type` 逻辑不稳定
   - 先把该类型暂时排除
   - 其余类型仍可先全量跑

一句话：

- `宁可晚一点全量，也不要带着错误口径把全库扫脏。`
